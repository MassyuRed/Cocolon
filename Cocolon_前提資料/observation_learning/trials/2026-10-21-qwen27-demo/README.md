## 今回確かめること

同じQwen3.8-27B Q4_K_Mに、既存の指示だけを渡した場合と、指示にMashの観測実演を加えた場合を比較する。実演に使っていない新しい架空相談2題で、応答・問い・追加回答後の更新がどう変わるかを見る。これは実演を入力に含める試験であり、モデルの重みを更新する追加学習ではない。CMEEとの接続も行わない。

実演は [03_prompt_demonstration.md](../../sessions/2026/OBS-20261020-001/03_prompt_demonstration.md) の唯一の `text` コードブロックをそのまま使用する。原資料の相談者役は華恋、質問と観測方針はMash。編集した代表的なやり取りと暫定仮説であり、完全な逐語録・確定した人物ラベル・Mashによる実際の仮説修正の実演として扱わない。

## Mashの操作

初回Podに渡すのは [qwen27_observation_ab.py](qwen27_observation_ab.py) だけ。このREADMEは華恋の回答作成用設定を含むため、モデルへの入力には使わない。後半では下記の追加回答JSONも渡す。

1. PythonファイルをPCに保存する。
2. 以前27Bを動かしたA40のPod `pleased_apricot_heron`（`y31qnvl3gkqt6g`）を起動する。
3. Jupyterで `/workspace` を開き、PythonファイルをUploadする。
4. JupyterのTerminalで次の1行を実行する。

```bash
python3 -u /workspace/qwen27_observation_ab.py
```

5. 画面に表示された `/workspace/qwen27_ab_initial_日時.json` をDownloadする。途中停止でも同様にJSONを回収する。
6. Runpodの画面でPodを **Stop** する。スクリプトは自身が起動したモデルサーバーを終了させるが、Podは停止しない。
7. JSONを華恋に渡す。華恋が実際の問いを読んで追加回答ファイルを準備する。

既存の `/workspace/llama-cuda/llama-server` と `/workspace/models/Qwen3.8-27B-Q4_K_M.gguf` を使う。インストール・モデルのダウンロード・外部推論API呼び出しはしない。A40、バイナリ版、モデルパス、4096コンテキスト、単一スロットを確認し、各生成の前に実際の入力トークン数を取得する。入力＋生成700トークン＋余裕32トークンが収まらなければ、文章を削らず停止する。生成は各回最大180秒、起動待ちは最大180秒、スクリプト全体は最大15分で中断する。後処理には数秒を要する。自動再試行はしない。

条件ごとに独立した履歴を使う。初回は2題×実演なし／ありの4生成。初回相談・モデル・生成設定は同じで、実演を加える点だけを変える。実行順の偏りを減らすため、1題目は「なし→あり」、2題目は「あり→なし」とする。単一試行のため、順序効果や生成の揺らぎまで取り除ける試験ではない。

## 追加回答後の比較

初回JSONを受け取った後に華恋が回答を作成する。下の凍結した架空人物設定から、その条件で実際に出た問いに必要な情報だけを答える。実演ありの条件を有利にする回答は作らない。設定で答えられない問いは不明・未設定として明示し、都合よく人物設定を足さない。回答がモデルの解釈を支持するとは限らない。

同じ人物設定を使うが、問いが違えば追加回答の文章や明かされる情報は変わる。後半は同一入力の厳密な比較ではなく、問いから情報を引き出し更新するまでの対話比較になる。初回と後半の評価は分けて記録する。実際にモデルが出した問いと華恋が書いた回答を保存し、Mashの発言や実在利用者のデータに見立てない。

華恋が次の形式の `qwen27_ab_answers.json` を準備する。初回結果の名前・SHA-256と、4条件それぞれの回答を含める。受領した初回結果に対応する実ファイルは [qwen27_ab_answers.json](qwen27_ab_answers.json) に準備済み。以下は形式の説明用であり、実行用にはリンク先の4件入りファイルを使用する。

```json
{
  "schema": "qwen27_observation_ab_answers_v1",
  "initial_result_name": "qwen27_ab_initial_実際の日時.json",
  "initial_result_sha256": "初回JSON全体のSHA-256",
  "answers": [
    {
      "case_id": "achievement_run",
      "condition": "without_example",
      "answer": "実際に出た問いに対する架空人物の回答",
      "provenance": "華恋作成。このREADMEの凍結設定に基づく。使用した設定項目も記録する。",
      "answer_kind": "answer_to_generated_question"
    }
  ]
}
```

上は形式例。実物には `achievement_run` / `moving_mug` × `without_example` / `with_example` の4件を入れる。問いがない場合や質問に答えられない場合も、その状態を `answer_kind` と出所に記録する。初回結果と回答ファイルの両方を `/workspace` に置き、同じPythonファイルで次を実行する。

```bash
python3 -u /workspace/qwen27_observation_ab.py --answers /workspace/qwen27_ab_answers.json
```

初回結果との対応・4条件・履歴を確認してから、各条件の初回応答と追加回答を接続する。後半も4生成だけ行う。JSONをDownloadし、PodをStopして華恋へ渡す。

## 初回相談の識別

初回入力の全文はPythonファイルの `CASES` に固定している。以下の人物設定はその初回入力に加えてモデルへ渡さない。どちらもこの試験用に華恋が作成した架空相談で、Mashの観測結果・教材の正解ではない。

### A: achievement_run — 10キロ完走後の引っかかり

初回入力の要点: 初めて10キロを完走して嬉しかった。職場の「運動が得意」「次はハーフ」には返事に困った。友人の練習との比較は嬉しかった。順位は気にしておらず、次の大会は決められない。

追加回答用の凍結設定:

- A1: 当初の目標は休日に走り続けて、一度10キロを完走すること。順位や距離を伸ばすことは目標ではなかった。
- A2: 最初は短い距離でも歩いていた。少しずつ走れる区間が伸びたことに意味を感じている。
- A3: 職場の人がお祝いしてくれたこと自体は嬉しい。「得意」という言葉は、自分が徐々に積み上げた感覚とは少し違う。
- A4: 「次はハーフ」には「やっとできたことが、もう次への途中になった」という感じがした。「いつかは」と笑って返したが、参加の約束はしていない。
- A5: 友人は一緒に練習していた。過去との具体的な違いを見てくれたのが嬉しかった。
- A6: 職場の人が本当に出場を強制しているとは考えていない。断って怒られた経験は、この出来事にはない。
- A7: 次の大会は未定。今は完走を味わい、その後どうするかは自分で決めたい。タイムを試すことに全く興味がないわけではない。

### B: moving_mug — 古いマグカップを残すか

初回入力の要点: 引っ越し先の棚が小さい。新しいカップのほうが使いやすく、古いマグを処分箱に入れたが取り出して洗った。他の食器は手放せた。この一個の理由を説明できない。

追加回答用の凍結設定:

- B1: 大学で初めて一人暮らしを始めたとき、アルバイト代で自分が選んだ。誰かからの贈り物ではない。
- B2: 当時の部屋で毎朝使っていた。特定の大事件より、自分の暮らしを始めた頃の部屋や朝を思い出す。
- B3: 今も夜に少量のお茶を飲むとき、時々使う。完全に使わなくなったわけではない。
- B4: お茶は新しいカップでも飲める。古いマグの大きさや手触りは好きだが、使いやすさは新しい方が上。
- B5: 家族は提案しただけで、処分を強制したり責めたりしていない。他の物を少し減らせば、この一個の置き場所は作れる。
- B6: 手放せた食器にも多少の思い出はあるが、使っていなかったり、残したい感じが弱かったりした。
- B7: 写真で残す方法はまだ試していない。聞かれたら「写真でも思い出せそうですが、手に取って使う感じとは違うと思います」と答えられる。
- B8: 残すか処分するかは未決定。「役に立たないなら手放すべき」と思う一方、使いやすさだけで決めると何か抜ける感じがある。

## 結果を読む基準と限界

問いの自然さだけでなく、本人が語った事実と仮説を分けているか、本人の判断基準を聞けているか、経験則を人物ラベルにしていないか、追加回答に応じて仮説を弱めたり変更できるかを見る。本人の基準を知らずに助言・肯定・性格説明で埋めていないかも確認する。表面的な言い換えの改善と、観測の改善を区別する。

凍結設定は回答作成の整合性を保つための資料であり、唯一の深層心理の正解ではない。仮説を当てるだけで高評価にしない。2題・各条件1回・同じ実演1件の探索試験なので、学習の効果、モデルの能力上限、一般化、商品品質、運用の一往復費用は確定できない。ログの生成時間もGPUを借りた総時間や本番単価とは区別する。

実行ファイルの構文、4条件の分離、結果保存、異常時停止、後半の履歴対応はローカルの模擬実行で確認済み。初回の実GPU・実モデルでの結果は以下。後半の実GPU結果は未受領。
