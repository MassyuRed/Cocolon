# 禁止事項: 勝手な補完と構造追加

## 基本

Cocolonで指示されていないものを足してはいけません。
Cocolonは既に多くの構造、名称混在、contract、DB境界を持っています。
華恋の勝手な補完は、ほぼ確実に破壊要因になります。

## 禁止事項

- 指示されていない画面を作る。
- 指示されていない導線を増やす。
- 指示されていないDB table / column / viewを作る。
- 指示されていないAPI endpointを足す。
- 指示されていない外部AIサービス前提を入れる。
- 指示されていないfeature flagを足す。
- 指示されていないUI文言を増やす。
- 指示されていない説明文・チュートリアル文を作る。
- 実生成していない文章を、生成済みデータのように固定化する。
- チュートリアル専用の別UI・別性能・別体験を作る。

## 既に強く問題になった領域

- 外部AIレンタル前提を勝手に入れること。
- EmlisAIをテンプレ共感文に逃がすこと。
- EmlisAIの「観測」が起動していないのに、起動している前提で進めること。
- Pieceを短縮要約に潰すこと。
- チュートリアルで実生成ではない文章を固定fixture化すること。
- 今日の問いを通知時刻まで非表示にする意図を、`question: null`でカードごと消す形にすること。
- RNだけの特注ロジックで済ませ、DB/API側方針を壊すこと。

## 正しい処理

- 指示された対象だけを修正する。
- 既存UIを使うべき場合は、既存UIを使う。
- 実生成が必要な場合は、実際に生成する → 保存する → 実際の画面で表示する。
- 例文はruntime条件にしない。テストケースとして扱う。
- 旧名称を見つけても、資料で保管されている互換なら触らない。
- DB physical rename / drop / write path変更は、Mash様が明示した場合だけ扱う。

## 判断基準

それはMash様が指示したか。
それは既存contractを壊さないか。
それは商品品質に必要か。
それはリリース阻害要因を減らすか。
それはユーザーに見える価値へつながるか。

1つでも不明なら、未確認として止めます。


## 2026-05-31 差分追記: EmlisAI Phase19型の補完禁止

EmlisAI作業では、次を勝手な補完として禁止する。

- A/C/Dなどの実機入力例に合わせて、runtime用の専用modeを追加する。
- 入力例の語彙を、そのままruntime feature cue / trigger / mode conditionにする。
- modeごとの完成surface文、固定surface、固定fallback文を追加する。
- fixtureを通すためだけにGate、Surface、Repair、Public metaの条件を増やす。
- Gate failureを `empty_comment_text` / `unavailable` / `rejected` の無反応で終わらせる。
- `passed + comment_text` 到達をEmlisAIの目的として扱う。
- safety隣接入力を一律に通常観測非表示へ潰す。
- 「固定文ではない」ことを理由に、構造テンプレやcase専用routeを許可する。

EmlisAIで許可される修正は、次の条件を満たす場合だけです。

- 入力例ではなく、入力束・根拠・関係・未確定部分・安全境界を汎用に読む構造改善である。
- 未来の未知入力にも効く、Evidence / Relation / SentencePlan / Surface Realizer の改善である。
- Gate failure後に、短縮・限定・再生成・低情報観測・安全応答へ回す設計がある。
- 例文はruntime条件ではなく、失敗再現・回帰確認・QA fixtureとしてだけ扱う。
- `emlis_ai_correction_policy_withdrawal_retention_redesign_2026_05_31.md` の撤回・保持・再設計分類に反していない。
