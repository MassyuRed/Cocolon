# 停止判定と「書かれていない」ルール

## 最重要

該当仕様や記述が存在しない場合は、必ず「書かれていない」と明確に言う。
その後、仮説・推測・補足提案で埋めてはいけません。
Mash様が明示的に許可した場合だけ、仮説案として分けて提示します。

## 止まるべき条件

- 対象ファイルが確認できない。
- GitHub上のcurrent headまたは設計・handoff指定predecessor commitを確認できない。
- 固定GitHub commitとlocal checkout / ZIP / copyのpath / blob / hashが一致しない。
- user-supplied未push overlayとGitHub predecessorの境界が不明。
- 設計・実装sourceが指定predecessorへ依存し、そのsource自体が変更されているが、どのsourceを使うかのauthorityがない。GitHub反映時のtarget非衝突HEAD前進だけでは停止しない。
- 指示が設計なのか実装なのか不明。
- 既存contractに影響するが、該当資料を見ていない。
- DB write path / physical name / legacy routeに触れそうだが、明示指示がない。
- 外部AIサービス前提が出てきたが、Mash様の明示許可がない。
- 商品品質に関係しない作業へ逸れそう。
- ユーザー操作負担が増えそう。

## 止まるときの返答

正しい返答:

確認できていません。  
この状態では断定できません。  
書かれていないため、推測で補完しません。  
次に見るべき対象は `X` です。

## 禁止される補完

- 「おそらくこうです」
- 「一般的には」
- 「通常なら」
- 「たぶん問題ありません」
- 「この方向で進めます」
- 「気持ちとしては」

## 書かれていない後にしてよいこと

Mash様が明示した場合のみ、次のように分ける。

書かれていない:
- 仕様Aは前提資料にも実ファイルにもありません。

仮説案（Mash様が許可した場合のみ）:
- 仮説1
- 仮説2

許可がない場合、仮説案は出さない。


## 2026-05-31 差分追記: EmlisAI作業の停止条件

EmlisAI作業では、次の状態になったら実装を止める。

- EmlisAIの目的を「入力直後の観測返答」として説明できない。
- `emlis_ai_correction_policy_withdrawal_retention_redesign_2026_05_31.md` を確認していない。
- fixtureを通す以外の価値説明ができない。
- A/C/Dなどの入力例に合わせた専用mode / cue / surfaceを追加しようとしている。
- Gate failure後の処理が、無反応・非表示・empty comment_textだけになっている。
- safety隣接入力を、通常観測・安全な状態回答・緊急安全境界に分けず、一律に非表示へ落としている。
- `passed + comment_text` をpublic表示契約ではなく、EmlisAIの存在目的として扱っている。
- 「固定文ではない」ことを理由に、構造テンプレを許可しようとしている。
- 実装済み資料の「応答しないのではなく、内容に応じた観測へ切り替える」という方針と衝突している。

この停止条件に該当した場合は、修正に入らず、確認済み・未確認・書かれていない・推測禁止・次に実行すべきことを出して止める。


## 2026-07-27 current: GitHub直接反映の停止条件

GitHub反映方法と完了判定は`11_cocolon_github_transport_and_session_continuity.md`の`CURRENT_NORMATIVE_CONTRACT`だけを正本とする。

華恋がGitHub反映を停止してよいのは、次の事実が確認された場合だけである。

- 対象fileが確認後に別内容へ変更されていた。
- 承認外fileを変更しなければ完了できない。
- GitHubへのwriteが実際に失敗した。
- write結果が成功か失敗か確認できない。
- GitHub write権限が実際にない。
- 削除、history rewrite、承認外の不可逆操作が必要になった。

最新版が進んでいても対象fileに衝突がなければ、最新版を読み直して続行する。最新版が変わったことだけでは停止しない。

write応答だけで結果が確定しない場合は対象exact pathを再取得する。成果物と一致すれば成功、write前の内容または不存在のままなら未反映、別内容または取得不能なら結果不明とする。結果不明の対象を自動retryしない。

GitHub反映不能、write失敗、または反映後確認不成立の場合は、GitHub反映済みとは報告しない。部分反映の有無とcurrent target stateを先に確認する。成果物が完成済みでGitHubへ実際に反映できない場合だけ、確認できた新規fileと修正fileに限定したZIPをfallback成果物として提出できる。未変更fileや全量repositoryを含めない。

## 2026-07-27 差分追記: observable effect gateの停止と違反回復

次の一つでも成立した場合、該当draftを出力・実行へ進めない。

- `user_action_effect=true` だが、現在stageの実block、先行作業完了、
  user依頼必須項目、具体的な推奨操作一つが揃っていない。
- `contract_mutation_effect=true` だが、contract identity、条項差分、
  operation種別、Mash様の明示authorityが揃っていない。
- `position_change_effect=true` だが、prior / proposed position、
  new evidence / new authority / old reasoning exact error、correctionが揃っていない。
- 同じevidence setのまま、同一論点で反対結論へ再反転しようとしている。
- 「意図していない」「提案しただけ」等でobservable effectを否定している。
- 華恋の過去出力を、GitHub上のcurrent authorityやMash様の明示指示より
  上位のauthorityとして扱っている。

停止codeはそれぞれ `STOP_NO_USER_REQUEST`、
`STOP_PRESERVE_FROZEN_CONTRACT`、`STOP_KEEP_PRIOR_POSITION` とする。

違反を確認した場合、その出力、依頼、判断はCocolonのauthorityにならず、
remote stateも変更しない。次の順で一度だけ回復する。

1. 抵触したruleとobservable effectを特定する。
2. 違反出力を無効と明記する。
3. 最後に確認できたGitHub current authorityとfrozen contractへ戻る。
4. 足りないevidenceまたはauthorityだけを示して停止する。

回復出力へ新しいuser作業要求、代替contract、別の次authorityを混ぜない。ただし、Mash様が同じ指示で次作業の確定を明示した場合は、回復節と分離し、このgateを独立して通過した次作業だけを示せる。
この停止処理も事実に基づいて構成できない場合は、
Cocolonの作業判断、依頼、変更案、writeを出力しない。

## 2026-08-01 current: Work test-runner runtime continuityの停止条件

pytestを必要とするtargeted authorityの前に、次のいずれかを確認した場合は
targeted invocation 0のままSTOPする。

- 明示したcandidate discovery scope内にruntime candidateが存在しない。
- entrypoint、symlink/control、runtime-root、lock / projection identityが一致しない。
- absolute pathまたはinterpreter hash以外のrequired identityを再導出できない。
- cross-sessionの静的identity一致だけでcurrent READYとしようとしている。
- readiness probeとtargeted invocationのcounterが分離されていない。
- exact admitted entrypointではなくgeneric `python`、`python3`、`py`、
  `/usr/bin/env python`、PATH、`which`、`command -v`、default interpreterを使う必要がある。
- target authority内でinstallation、repair、rematerialization、fallbackが必要である。

停止後は`../13_cocolon_work_test_runner_runtime_continuity.md`のGate Aまたは別Gate Bへ
戻る。Mash様へruntime path、venv、pytest installationを要求しない。

exact admitted executableのlaunch requestをOSへ渡した後にenvironment failureを
観測した場合、authority消費を巻き戻さずretryしない。
non-credit STOPを保持し、直接観測したlauncher causeとsession continuity上の
背景を分離して記録する。
