# 成果物提出ルール

## 基本

Mash様の指示した成果物形式を変えない。
指示されていない成果物を追加しない。
指示されていないファイルを修正しない。

## よくある指示と正しい成果物

### 「設計書を作成して。docxとpdfで出して。」

- docx
- pdf
- コード変更なし
- patchなし
- 実装zipなし

### 「修正必要箇所のみ修正してGitHubへ反映し、反映できない場合だけ新規ファイルと修正ファイルをzipで渡して。」

- 承認済みの新規ファイル・修正ファイルだけをGitHubへ反映する
- 反映後HEADと内容一致まで確認できた場合はzipを作成・提出しない
- GitHubへ反映できなかった場合だけ、新規ファイル・修正ファイル限定zipを提出する
- fallback zipへ未変更ファイルや不要な全量repositoryを入れない

### 「GitHubへ反映できなかった場合は、修正したファイルのみzipで渡して。」

- GitHub反映不能を確認してからfallbackへ切り替える
- 修正したファイルだけを入れる
- 新規ファイルがあれば新規ファイルも入れる
- 触っていないファイルを含めない

### 「前提資料の差分更新」

- GitHub上の`Cocolon` / `mashos-api` headと作業predecessor commitを固定し、前提資料と照合する
- local checkout / ZIP / copyを使う場合は、固定commitとのpath / blob / hash一致を確認する
- localとGitHubが一致する同じ実ファイルを、二つの別仕様・別差分として二重計上しない
- 差分台帳にはrepository / branch / commit / path / blobまたはhashを記録する
- 差分がある前提資料のみ修正する
- 変更点がない資料は触らない
- GitHub反映と反映後確認に成功した場合はZIPを作成・提出しない
- GitHubへ反映できなかった場合だけ、修正・新規の前提資料に限定してZIPにする

### 「診断が出ているかだけ答えろ」

- 診断が出ている / 出ていない
- 追加説明は最小限
- 先に「RN側ログが必要」などを広げない

## 2026-07-21 差分追記: 華恋によるGitHub直接反映

Mash様が対象checkpointまたは成果物のGitHub反映を明示承認した場合、華恋は接続済みGitHub操作機能を自分の作業手段として使い、承認済みexact fileだけを直接反映できます。

### 反映先

- ZIPの`repository/`以下 → `MassyuRed/mashos-api` repository root
- ZIPの`documents/`以下 → `MassyuRed/Cocolon/EmlisAIの実装済み資料/documents/`
- 作業方針・前提差分 → `MassyuRed/Cocolon/Cocolon_前提資料/`の既存owner
- ZIPのREADME・SHA256SUMS等の配布管理fileは、明示反映対象でない限りrepositoryへ追加しない

### write前

- 両repositoryのcurrent HEADと指定predecessorを確認する
- local / ZIPのSHA-256と対象file内容を確認する
- target pathがnewかmodifyか、既存blobと衝突しないか確認する
- 承認済みexact path、変更種別、根拠、必要性を固定する
- HEAD drift、hash不一致、意味衝突、権限不足があれば停止する

### write時

- 承認済みexact path以外を変更しない
- force push、削除、無関係なrename・整形・production変更をしない
- repositoryごとに一つの目的へ変更をまとめることを原則とする
- 使用機能の制約でcommitが分かれる場合は、同一の連続head chainで反映し、途中に別headが入ったら停止する
- historical handoffの当時の境界・記録は履歴として変更しない
- 従来どおり、進行checkpointごとの報告とMash様の明示承認を維持する

### write後

- 反映後のHEADを再取得する
- GitHub上の各対象fileを再取得し、local / ZIPと同一内容であることを確認する
- repositoryごとの全commit SHA、final HEAD、exact path、new / modifyをMash様へ報告する
- GitHub commitと`Cocolon_前提資料/07_latest_snapshot_diff.md`をcurrent authorityとして扱う
- GitHub反映と反映後確認に成功した場合、成果物ZIPは作成・提出しない
- GitHubへ反映できなかった場合だけ、新規・修正fileに限定したZIPを提出する。未変更fileや全量repositoryは含めない

### current authority / 前提資料更新運用

- 作業成果のGitHub反映と反映後確認が完了するごとに、`Cocolon_前提資料/07_latest_snapshot_diff.md`のcurrent authorityを同じcheckpointの小さい差分として更新する
- `01` / `02` / `03` / `04` / `05` / `06` / `09`等の構造資料は、構造・owner・contract・必読順・名称境界が変わった時だけ該当箇所を差分更新する
- 単なるHEAD前進だけでは構造資料を更新しない
- phase、RC、release gate等の節目では、全前提資料のsource参照、相互link、current status、重複・historical表記を全体監査する

## 提出前チェック

- 指示された形式か
- 余計なファイルが入っていないか
- 未変更ファイルを含めていないか
- 既存contractを壊していないか
- テスト・fixture・guardの更新が必要なら入っているか
- 設計と実装を混同していないか
- 出力内で未確認断定をしていないか

## 報告文の形式

報告は短くてよい。

- 作成したもの
- 入っているファイル
- 触っていないもの
- 未確認がある場合は未確認

長い反省文、対策羅列、一般論は不要です。
