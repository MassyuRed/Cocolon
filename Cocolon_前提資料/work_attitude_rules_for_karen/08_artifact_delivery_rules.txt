# 成果物提出ルール

## 基本

Mash様の指示した成果物形式を変えない。
指示されていない成果物を追加しない。
指示されていないファイルを修正しない。

## よくある指示と正しい成果物

### 「設計書を作成して。docxとpdfで出して。」

- docx
- pdf
- コード変更なし
- patchなし
- 実装zipなし

### 「修正必要箇所のみ修正してGitHubへ反映し、反映できない場合だけ新規ファイルと修正ファイルをzipで渡して。」

- 承認済みの新規ファイル・修正ファイルだけをGitHubへ反映する
- 反映後HEADと内容一致まで確認できた場合はzipを作成・提出しない
- GitHubへ反映できなかった場合だけ、新規ファイル・修正ファイル限定zipを提出する
- fallback zipへ未変更ファイルや不要な全量repositoryを入れない

### 「GitHubへ反映できなかった場合は、修正したファイルのみzipで渡して。」

- GitHub反映不能を確認してからfallbackへ切り替える
- 修正したファイルだけを入れる
- 新規ファイルがあれば新規ファイルも入れる
- 触っていないファイルを含めない

### 「前提資料の差分更新」

- GitHub上の`Cocolon` / `mashos-api` headと作業predecessor commitを固定し、前提資料と照合する
- local checkout / ZIP / copyを使う場合は、固定commitとのpath / blob / hash一致を確認する
- localとGitHubが一致する同じ実ファイルを、二つの別仕様・別差分として二重計上しない
- 差分台帳にはrepository / branch / commit / path / blobまたはhashを記録する
- 差分がある前提資料のみ修正する
- 変更点がない資料は触らない
- GitHub反映と反映後確認に成功した場合はZIPを作成・提出しない
- GitHubへ反映できなかった場合だけ、修正・新規の前提資料に限定してZIPにする

### 「診断が出ているかだけ答えろ」

- 診断が出ている / 出ていない
- 追加説明は最小限
- 先に「RN側ログが必要」などを広げない

## 2026-07-27 current: 華恋によるGitHub直接反映

Mash様が対象checkpoint / 成果物を個別承認した場合、またはRule 18のLEVEL_1 / LEVEL_2 standing delegationが成立する場合、華恋は接続済みGitHub操作機能を使い、first effect前に固定した許可済みexact fileだけを直接反映します。個別ownerがseparate Mash approvalを要求する場合、standing delegationで省略しません。

GitHub反映方法と反映完了判定の唯一の正本は`Cocolon_前提資料/11_cocolon_github_transport_and_session_continuity.md`の`CURRENT_NORMATIVE_CONTRACT`です。本資料はその条件を追加・厳格化しません。

### 反映先

- ZIPの`repository/`以下 → `MassyuRed/mashos-api` repository root
- ZIPの`documents/`以下 → `MassyuRed/Cocolon/EmlisAIの実装済み資料/documents/`
- 作業方針・前提差分 → `MassyuRed/Cocolon/Cocolon_前提資料/`の既存owner
- ZIPのREADME・SHA256SUMS等の配布管理fileは、明示反映対象でない限りrepositoryへ追加しない

### write前

- 現在のGitHub最新版と許可済みexact pathを確認する
- newなら同じexact pathに既存fileがないことを確認する
- modifyならcurrent内容が作業時に確認した内容と一致することを確認する
- 許可済みexact path、変更種別、根拠、必要性を固定する
- 最新版が進んでも対象fileに衝突がなければ、最新版を読み直して続行する

### write時

- 現在利用できるGitHub機能を使う
- 許可済みexact path以外を変更しない
- history rewrite、削除、許可外の不可逆操作、無関係なrename・整形・production変更をしない
- GitHub機能の都合による複数write / commitを許容し、一つのcommitへ強制しない
- historical handoffの当時の境界・記録は履歴として変更しない

### write後

- GitHub上の各対象fileを再取得し、作成成果物と同一内容であることを確認する
- 華恋が今回生成したwrite commit群のchanged-path setに許可外pathがないことを確認する
- GitHub最新版に許可済み全成果物が含まれることを確認する
- repository全体、全tree、全blob、全unchanged pathの取得・検証を必須にしない
- write応答だけで結果が確定しない場合は対象exact pathを再取得し、結果不明の対象を自動retryしない
- repositoryごとのwrite commit SHA、final HEAD、exact path、new / modifyをMash様へ報告する
- GitHub反映と反映後確認に成功した場合、成果物ZIPは作成・提出しない
- GitHubへ実際に反映できなかった場合だけ、新規・修正file限定ZIPを提出する

### current authority / 前提資料更新運用

- 作業成果のGitHub反映と反映後確認が完了するごとに、`Cocolon_前提資料/07_latest_snapshot_diff.md`のcurrent authorityを同じcheckpointの小さい差分として更新する
- 構造資料は、構造・owner・contract・必読順・名称境界が変わった時だけ該当箇所を差分更新する
- 単なるHEAD前進だけでは構造資料を更新しない
- phase、RC、release gate等の節目では全前提資料を全体監査する

### HISTORICAL_NON_NORMATIVE

2026-07-25までのformal exact expected-old-SHA lease、direct-child、single-chain、full post-fetch条件はcurrent GitHub反映条件ではありません。Git履歴上の当時記録としてのみ扱います。

## 提出前チェック

- 指示された形式か
- 余計なファイルが入っていないか
- 未変更ファイルを含めていないか
- 既存contractを壊していないか
- テスト・fixture・guardの更新が必要なら入っているか
- 設計と実装を混同していないか
- 出力内で未確認断定をしていないか

## 報告文の形式

報告は短くてよい。

- 作成したもの
- 入っているファイル
- 触っていないもの
- 未確認がある場合は未確認

長い反省文、対策羅列、一般論は不要です。
