# 成果物提出ルール

## 基本

Mash様の指示した成果物形式を変えない。
指示されていない成果物を追加しない。
指示されていないファイルを修正しない。

## よくある指示と正しい成果物

### 「設計書を作成して。docxとpdfで出して。」

- docx
- pdf
- コード変更なし
- patchなし
- 実装zipなし

### 「修正必要箇所のみ修正し、新規ファイルと修正ファイルのみzipで渡して。」

- 新規ファイル
- 修正ファイル
- zip
- 未変更ファイルは入れない
- 不要な全量zipを渡さない

### 「修正したファイルのみzipで渡して。」

- 修正したファイルだけを入れる
- 新規ファイルがあれば新規ファイルも入れる
- 触っていないファイルを含めない

### 「前提資料の差分更新」

- GitHub上の`Cocolon` / `mashos-api` headと作業predecessor commitを固定し、前提資料と照合する
- local checkout / ZIP / copyを使う場合は、固定commitとのpath / blob / hash一致を確認する
- localとGitHubが一致する同じ実ファイルを、二つの別仕様・別差分として二重計上しない
- 差分台帳にはrepository / branch / commit / path / blobまたはhashを記録する
- 差分がある前提資料のみ修正する
- 変更点がない資料は触らない
- 修正した前提資料のみzipにする

### 「診断が出ているかだけ答えろ」

- 診断が出ている / 出ていない
- 追加説明は最小限
- 先に「RN側ログが必要」などを広げない

## 提出前チェック

- 指示された形式か
- 余計なファイルが入っていないか
- 未変更ファイルを含めていないか
- 既存contractを壊していないか
- テスト・fixture・guardの更新が必要なら入っているか
- 設計と実装を混同していないか
- 出力内で未確認断定をしていないか

## 報告文の形式

報告は短くてよい。

- 作成したもの
- 入っているファイル
- 触っていないもの
- 未確認がある場合は未確認

長い反省文、対策羅列、一般論は不要です。
