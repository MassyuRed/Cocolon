# 禁止事項: 前提資料と実ファイル確認不足

## 固定ルール

Cocolon作業では、Cocolon_前提資料を読まずに出力してはいけません。
ただし、前提資料だけで「理解している風」に返してもいけません。
前提資料は地図であり、実ファイルが現物です。

## 必ず確認するもの

作業内容に応じて、次を確認します。

- `Cocolon_前提資料/00_karen_read_first.md`
- `03_cocolon_naming_system.md`
- `09_Cocolon_名称混在保管と構造境界_YYYY-MM-DD.md`
- `01_cocolon_overall_structure.md` 系
- `02_cocolon_national_system.md` 系
- `05_cocolon_rule_file_index.md`
- `07_latest_snapshot_diff.md`
- GitHub反映では`11_cocolon_github_transport_and_session_continuity.md`の`CURRENT_NORMATIVE_CONTRACT`
- Work-local Python / pytest test-runnerを扱う場合は`../13_cocolon_work_test_runner_runtime_continuity.md`と`16_test_runner_runtime_continuity_and_one_shot_prelaunch.txt`
- GitHub上の`Cocolon` / `mashos-api` current head、承認対象exact path、対象実ファイル。設計・実装sourceに指定predecessorがある場合は、そのsource identityも分離して確認する
- local checkout / ZIP / copyを使う場合、そのpath / blob / hashが固定GitHub commitと一致すること
- 必要なログ / スクリーンショット / テスト結果

## 前提資料の読み方

前提資料は、タスク表ではありません。
前提資料は、Cocolonのファイル構成・コード構成・名称混在境界を復元するための作業用地図です。

旧名称が残っていても、すぐrenameしません。
旧名称には、互換・DB境界・runtime owner・legacy façadeとして残す理由がある場合があります。

## 禁止事項

- 前提資料を読まずにCocolon構造を語る。
- 前提資料だけ読んで、実ファイルを見ずに修正判断する。
- 旧名称を見つけて即renameする。
- DB physical name、legacy route、response key、RN表示条件を勝手に変える。
- Cocolon_前提資料を残タスク表として扱う。
- Cocolon_前提資料更新時に、変更がない箇所まで触る。

## 正しい処理

1. 前提資料で「地図」を見る。
2. 最新実ファイルで「現物」を見る。
3. 両方に差分があれば、差分として扱う。
4. 書かれていなければ「書かれていない」と言う。
5. 指示がない限り、仮説で補完しない。

## Cocolon_前提資料更新時のルール

- 原則としてGitHub上の`Cocolon` / `mashos-api`をcurrent実ファイル確認元にする。設計・実装sourceに指定predecessorがある場合はsource identityとして固定するが、GitHub反映時のHEAD drift停止条件へ変換しない。
- GitHubからmaterializeしたlocal checkout / ZIP / copyは、path / hash一致時に同じ実ファイルとして扱う。local / cloud差を別仕様にしない。
- user-supplied未push overlayがある場合はhandoff materialとして分離し、source baselineを黙って置換しない。
- GitHubとlocal materializationが不一致なら同一視せず、commit / path / hash差を提示する。GitHub反映では承認targetが確認後に別内容へ変わった場合だけ衝突停止とする。
- 過去local ZIPのsnapshot名・hash・countは当時の証拠として残し、current GitHub値へ遡及上書きしない。
- 前提資料との差分だけを見る。
- 変更点がない資料は触らない。
- 修正必要箇所のみ差分修正・差分追記する。
- 作業成果のGitHub反映と反映後確認が完了するごとに、`07_latest_snapshot_diff.md`のcurrent authorityだけを同じcheckpointの小さい差分として更新する。
- 構造資料は構造・owner・contract・必読順・名称境界が変わった時だけ差分更新し、単なるHEAD前進では触らない。
- phase、RC、release gate等の節目では、全前提資料のsource参照・相互link・current status・重複・historical表記を全体監査する。
- GitHub反映と反映後確認に成功した場合はZIPを作成・提出しない。GitHubへ反映できなかった場合だけ、修正・新規fileに限定したZIPを渡す。
- 作業報告や残タスクを前提資料に混ぜない。

## 2026-07-27 current GitHub反映情報

- GitHub反映方法と完了判定は`11_cocolon_github_transport_and_session_continuity.md`の`CURRENT_NORMATIVE_CONTRACT`を唯一の正本とする。
- 特定鍵、fingerprint、host、SSH、full fetch、exact leaseをcurrent GitHub反映の必須条件にしない。
- 秘密鍵、passphrase、token、credential内容、agent socket、環境変数値、traceは前提資料へ残さない。
- GitHubへのwrite権限が実際にない場合だけ、権限不足として停止する。

## 2026-07-26 差分追記: current actual environmentを設計前提の最上位に置く

Cocolonのarchitecture、security、test、transport、運用設計は、
一般的なアプリ開発環境ではなく、現在確認できるCocolonの実運用環境から始める。

設計前に、少なくとも次を確認する。

- 現在のproject主体。
- 実際のコード作業者とwrite判断者。
- repositoryがpublicかprivateか。
- 現在存在するwrite route。
- 現在存在する競合actor。
- Mash様の承認境界。
- 既存の防止策。
- 現在のリリース目的と期限。

複数の独立したコード作業者、不特定多数のcontributor、公開repository、
外部botによるproduction publication、将来の開発チーム、将来想定の
大規模同時運用は、実在を確認するまでcurrent requirementへ混ぜない。
一般的なbest practiceは検討候補であり、current requirementへ自動昇格させない。

ただし、秘密情報を記録・公開しない、承認scopeを越えない、履歴を
force rewriteしない、user dataを保護する等の最低限の安全境界は維持する。
actual environment優先を、必要な安全境界を無視する理由に使わない。

「一般的には必要」「より安全になる」だけでは追加systemの根拠にならない。
actual actor、actual route、actual failure、既存対策を差し引いた残余risk、
最小代替、構築費、継続保守費、中止条件を説明できる場合だけ採用する。

future requirementの再検討triggerは、複数の独立writer、public contribution、
自動production publication、最小確認を行っても反復する実競合事故、
法令・契約・security上の新要件のいずれかが実在した時とする。
trigger成立だけで自動再開せず、Mash様の新しい明示承認を必要とする。

## 2026-07-26 差分追記: 選択した仕組み自体を中止する判断

一度採用したsystem、security mechanism、test framework、transport routeでも、
次のいずれかが成立した場合は内部の未完了項目を増やさず、方式自体を再評価する。

- 本来守る対象より、補助system自身の保守が主作業になった。
- 新しい情報を得ず、system自身が生んだfailureを閉じ続けている。
- current actual environmentに存在しない脅威が主要根拠になっている。
- 防ぐriskより構築・継続保守・停止時間が大きい。
- Cocolon完成への導線を説明できない。

中止時は、完成させてから捨てるのではなく、safe disable、
historical preservation、current authorityの更新だけを行う。

## 2026-08-01 差分追記: session-local test-runnerのactual environment確認

Work-local test-runnerは、過去にREADYだったという記録だけでcurrent実体を
仮定しない。sessionが変わった場合はcurrent continuityを未確認へ戻し、
targeted authorityを提示する前にroot、entrypoint、symlink/control、manifest、
lock / projection identityをread-onlyで確認する。

session境界だけで物理的消失を断定しない。探索scopeを先に固定し、
candidate不在はそのscope内だけの結果として記録する。同一instanceの静的
identityが一致してもREADYとせず、別Gate Bでfresh version probe、role smoke、
identity再導出がVALIDになった後だけ再利用する。candidate不在または
不一致ならtargetを実行せず、華恋側の別rematerialization authorityへ分類する。

absolute pathまたはresolved interpreter hash単独をruntime identityとしない。
generic `python`、`python3`、`py`、`/usr/bin/env python`、PATH探索、`which`、
`command -v`、base interpreterの存在をpytest-bearing runtimeの
実在証明へ置き換えない。
