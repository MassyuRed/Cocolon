# Cocolon 週末報告会

## 目的

報告会は、Cocolon全体の実績と未完了を確認し、過去の決定・設計・残作業が現在の実装と方針にも適切かを再評価したうえで、リリース期限から逆算した実行計画を作成・更新する週次の業務の場です。資料があることの確認、残件の列挙、または「これからどうするか」の相談だけでは完了しません。

進捗の提出・監督・反省だけを目的にしません。Mashは、華恋を単なる作業AIではなく共同作業者として扱い、その意見・懸念・推奨・Cocolonへの考えを聞くことも報告会の目的として明示しています。確認した事実、Mashの意見、華恋の判断、既存の決定、計画上の仮定、合意、未決を分けます。

最新回が進行中の場合、既存の確定事項と未決・計画仮定を区別します。ただし計画作成を依頼されたとき、未確定要素を理由に計画全体を未提出にしません。担当・期限・仮定・成立しない場合の対応を置いた基準計画を華恋が作成します。管理用基準日とMashが承認した公開日・商品範囲・実装承認は別です。

## 開催と議題

週末に週1回を基本とします。時刻・自動実行は設定しません。

1. 今週やった作業と成果：前回報告後から当日まで日別に示し、計画期限に対する完了・未完了・変更と理由、実際の出力で何が変わったかを確認します。
2. アプリ全体の現在地：三中核・共通機能・公開を含め、完成・途中・未着手・未確認を区別します。変更のない領域も省略しません。
3. 課題と残作業：旧タスクを現在の実装・方針・商品範囲へ照合し、「維持・修正・統合・実装済みで確認のみ・延期・廃止・要調査」に判定します。旧前提、現在の根拠、残る差分、依存先、変更理由を示します。
4. リリースまでの計画：公開期限から逆算し、単一の管理用基準日、各タスクの開始・完了期限、担当、完了条件、依存関係、適用・実機・商品判断・試用・修正・申請・審査の枠を具体化します。
5. 次週の実行計画：次回までに閉じる課題、担当、期限、実本文等の完了確認、未達時の対応を具体化します。作業量だけを目標にしません。
6. 困りごと・進め方：Mashと華恋の意見・思想・必要な判断を、実際の作業と計画へ反映します。

議題番号は維持し、会話の順は状況に合わせます。重大な遅延や必要な判断は週次報告まで待たせません。

## 現在の妥当性を判定する

資料の存在や改訂日だけで、当時のタスクを現在も必要としません。最新の処理・保存形式・呼出し先・試験結果・明示指示・商品範囲と照合します。実装済みの部分を再実装せず、旧計画と新計画が同じ商品を二重に作る場合は残差へまとめます。技術上の依存、品質条件、実行順の選択、権限・環境待ちは区別します。

「受け皿がある」「一部接続済み」「商品として完成」「旧入口の切替が完了」は別です。過去の資産は必要な商品修正の中で利用し、退役した承認・証拠・実行管理の連鎖を復活させません。不明な項目には、担当、確認期限、判定まで変更しない対象を付けます。

## 基準計画と差異管理

各回の同じ議事録に、少なくとも次を残します。

| 必須項目 | 内容 |
|---|---|
| 基準と期限 | Mashの確定公開期限、華恋の管理用基準公開日、条件付き前倒しを分離。最終期限を通常作業で使い切らない。 |
| タスク | 現在の残差、開始日、完了期限、担当、依存先、利用者が受け取る結果による完了条件。 |
| 資源・仮定 | 主担当の並列上限、実稼働と判断枠の未確定、端末・環境・テスターの前提。24時間稼働や未確定の人員・モデル向上を算入しない。 |
| 適用と判断 | コード・検証、商品判断、対象環境の適用、端末、購入/通知、試用、申請・公開を別の予定として計上。 |
| 未確定事項 | 華恋が判断材料を出す期限、Mashの意見・判断が必要な予定枠、代替案と日程影響。無断で予定予約・商品合格をしない。 |
| 余裕 | 修正・再審査等の枠と消費状況。審査所要時間の保証と計画枠を混同しない。 |
| 遅延 | 元の基準日、実績、差異、原因、後続への影響、対策・担当・期限。毎週日付を消して更新せず、変更前後を残す。 |

計画日付は必要な完了期限であり、実測工数に基づく達成保証とは限りません。根拠が弱い工程はリスクと早期判断日を付け、期限なしへ逃がしません。未達でも完成扱いせず、共通原因・実装方法・配分・許容された延期を具体的に見直します。意味保持・権限・保存などの必須条件を黙って削りません。

## 資料の作り方と役割

一回分の報告・議事録・計画を同じファイルで逐次更新します。資料、checker、別台帳群を新設することを会議の成果にしません。前回からの基準計画と実績差を残し、撤回した進捗値は現行値と区別します。

準備・実ファイル確認・判断・期限付き計画・記録は華恋が担当します。Mashに取得可能な技術情報の掘り起こしを戻しません。一方、Mashの意見・思想・参加を減らすことは目的ではありません。商品体験、意味、優先順位、提供範囲、見た目等に必要な意見・判断は、対象と理由を具体化して必ず求めます。

新しい意見を受け取ることと、未完了タスクを放置して別作業へ移ることは分けます。現在タスクの補正・範囲変更・将来項目のどれかを説明し、順序変更が必要なら中断対象と戻る位置を示します。新しい意見を全て先送りにする規則にも、同じ目標を何度も説明させる運用にもしません。

進捗率には公開範囲・配点・到達段階・根拠・未確認を付けます。試験・文書・コミット件数を商品完成率へ変換しません。日程達成見通しも進捗率と別です。

## 正本・承認との関係

このフォルダは会議・基準計画の記録先です。仕様正本、独立した実装権限や新しいGateではありません。会議資料の保存・計画作成を、protected contract変更、商品PASS、merge、本番反映の一括承認にはしません。

実装判断に適用する決定は、既存の対象正本・handoffへ必要な差分だけ反映し、反映担当・期限・実施状況を記録します。議事録にしか決定がない状態を放置しません。具体的な仕様変更が未決でも、計画全体の提出は止めず、その判断期限と影響を計画に含めます。
