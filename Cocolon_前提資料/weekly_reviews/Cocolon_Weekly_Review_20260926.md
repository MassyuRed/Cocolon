### 3.4 Piece — 接続済みの生成を、保存済み入力と実アプリの体験へつなぐ

意味処理と文章編集には、未対応の表現・照応・共有向け変換・自然さの残差がある。画像も開発用PNGの確認であり、端末のrenderer・保存・共有の合格ではない。入力を読み取れていないのに原文や埋草を出すこと、意味を削って収めること、正当な不明を勝手に補うことは解決にしない。

利用導線として残るのは、認証された本人の保存入力を取得し、対象版を照合し、元入力と許可された補足・更新後の内容を区別してPieceへ渡す接続。その後の実アプリpreview、保存、履歴、再書出し、native画像保存・共有、プラン・回数・公開範囲・削除との結合も残る。既存保存構造や部品が存在することと、通しで使えることは別である。

完了条件の中心は「本人の保存済み入力を選ぶ→原意を保ったPieceを確認する→保存する→履歴から同じ内容を再表示・再書出しする→許可された範囲へ共有できる」という既存の一連の体験。認証、補足のsource権限、版、公開範囲、回数、削除の境界を併せて検証する。各段階の既存契約を変更する場合は、必要な個別承認と技術設計の境界を守る。

最新`5887cec`の選択検査は69ファイル・5,090件＝4,957 PASS / 133 FAIL / 0 ERROR / 0 SKIP。今回追加76件は成功し、旧5,014件の成否と失敗詳細は不変だが、全成功ではない。この133件をEmlisの455件と合算せず、現行仕様・本文・意味保護との関係を確認する。保存された入力の再実行や開発PNGの検査も、この分母へ足さない。

前回の「CMEEのPiece入口を作る」という旧未完了を更新する。一方、Emlisの完成を待たずに原入力を起点としたPieceを進められることと、許可された回答・補足を使う保存契約の接続が不要であることは別。Emlisの生成した応答文をPieceのsourceへ転用しない。

華恋の懸念は、個別構文と改行の修正だけが続き、アプリで利用できる状態の完成が先送りになること。改善済みの本文・画像を継承し、品質の残差と利用導線の残差を別々の完了条件で閉じることを推奨する。汎用日本語理解や、あらゆる文末の対応完了を接続開始の新条件にしない。

**DB・API・端末。** Emlisの保存/API/RNコードやSQLは存在するため、一から再実装する残件ではない。対象環境、必要schema・migration、認証・権限、実APIから画面へ戻る一往復、再開・再取得・履歴までの適用と通し確認が必要。前回9/19のDB読取結果を本日の実DB状態へ無条件に引き継がない。本節報告時点では接続先DBを再照会していない。後続の議題2の限定した再照会結果は§2.4へ分離する。

**横断機能。** 別アカウントからの閲覧禁止、入力・生成物の削除、公開範囲変更、遅延応答・二重実行・回数、Home/入力/下書き/日跨ぎ、旧問いとの重複、Nexus/EmotionLog/通知遷移・未読等の整合は、既存実装を使った確認と必要な修正として残す。全項目に不具合が発生しているという意味ではなく、前回の受入れ残件を完了と判定する根拠が不足しているという区別を置く。

### 3.9 華恋の追加指摘・意見 — 作業を続ける単位から、完成させる単位へ

以下はMashの意見を代筆したものではなく、議題1・3の実績と未完了を踏まえた華恋の判断・推奨である。この追加意見へのMashの賛否はまだ記録していない。

**利用可能量による切替には賛成。ただし、稼働量と完成への前進は分ける。** Workを使える間にEmlisAIの品質改善へ集中し、回復待ちをPieceの実装へ充てる方針は、今回示された利用制約と領域別分担に合っていると考える。一方、使用量を使い切ったことだけでは、既知の欠陥を閉じたことや期限達成の根拠にはならない。各作業では、どの問題を共通原因から解決し、実出力・一連の体験で何が変わったかを確認する。

**最も強い懸念は、個別表現の修正が終わりのない主作業になること。** 今週の限定修正とPieceの接続は実際の前進であり、すべてを無駄な条件追加とは扱わない。しかし、同じ意味関係で言い方が変わるたびに次の局所修正へ移るなら、入力の受取り・意味の選択・文章化の共通箇所で閉じられる問題かを検討すべきである。これは現状の全失敗の原因を確定した報告ではなく、作業単位の選択への指摘。使える既存構造は継承し、妨げになる実装方法は因果箇所で変える。品質を下げたり別エンジンを作ったりする提案ではない。

**意味を守ることと、原文の表現を固定することを混同しない。** EmlisAIは本人が考える材料になること、Pieceは元の会話を知らない他者にも考えや価値観が伝わることが重要である。必要な意味・根拠・主体・時点・条件・留保を保つことと、表現を自然に編集することは別々に確認する。本文が生成された、全語句が残った、画像に収まったという技術結果だけで、それぞれの商品目的を満たしたと判定しない。根拠のない説明を足す、重要な意味を削る、保留を断定へ変えることも解決にしない。根拠は本議事録§3.3〜3.4と前回議事録§6.9〜6.10。

**Pieceの実アプリ接続と、課金・権限・実機の作業枠を失わない。** 最新Piece記録では認証付き保存入力・実アプリpreview/save/history/native save/shareが残り、現行IAPにも§3.5の未解消箇所がある。EmlisAIとPieceの内部文章処理だけで全ての利用可能枠が埋まると、共通機能がさらに後ろへ押し出される懸念がある。Pieceの許可された実装範囲では保存入力からプレビュー・保存・履歴・共有へつなぐ一連の体験を完成単位に含め、共通機能は担当・実行枠・完了条件を計画に明記することを推奨する。個別の必要な承認を省略したり、ここで配分を再変更したりはしない。

**切替時の手戻りと検査の意味を管理する責任は華恋が持つ。** Mashへ同じ前提の説明や再開位置の掘り起こしを繰り返させない。既存の失敗は商品欠陥・旧期待との衝突・検査/実行問題を分け、共通原因をまとめられる範囲ではまとめて扱う。件数を減らすための無断の除外・期待更新はせず、前後比較と残る意味保護を示す。議題3で列挙した残件を、次の作業でも別名にして持ち越すことを避ける。

未完成と無価値は同じではない。今週のPieceの生成経路接続と出力改善は認める。その前進を商品として受け取れる状態まで届けることが、次に華恋が重視すべき仕事だと考える。今回の議事録更新そのものを製品品質の改善や全体進捗の加点にはしない。

### 5.3 Work / EmlisAIの進め方 — 保存済みの続きから、共通原因を一群ずつ閉じる

本文の優先対象は、元入力と回答にある重要な感情・関係を取り落とさず、初回と回答後の観測・フォローで、原文再掲と重複だけにしないこと。主体・否定・条件・時点・不確実さを壊す実不具合や、対象として返すべき本文の未提供を先に扱い、その意味を読みやすい焦点・対比・関係として返すところまで同じ完成単位に含める。

10/03の区切りでは、選定した群の既知の意味欠落・誤帰属と明白な文章不成立が解消し、必要な初回→回答→訂正→撤回→保存後の再表示が、同じ変更版で説明できることを目標にする。同じ100入力と継承保存状態に必要な比較を、影響範囲に対応して確認する。同一性と無影響を説明できる部分は継承し、毎回の全検証や全文再読を無条件で繰り返さない。保護すべき意味の改変を検出できることと、実本文の価値の両方を確認する。未解決がある群は未完了とし、Mashによる正式商品合格を代筆しない。

### 5.4 Pro / Pieceの進め方 — 原入力からプレビューを先に通し、保存・履歴へ伸ばす

次のPro枠では、現在の未完了差分を安全に継承したうえで、主たる実装対象を「対応語尾の追加」から「保存原入力→既存生成→プレビューという一連の接続」へ進めることを推奨する。前提は、§14で接続済みのCMEE Piece consumer・canonical本文・既存B9である。source snapshot内のowner照合だけで、認証済み取得ができたと扱わない。

最初に、B5と既存の保存/API/RNの実ファイルを照合し、本人の認証・保存入力ID・版・削除/アクセス可否を確認して既存sourceへ渡す、必要な差分を実装する。次に、その同じ入力を既存consumerで文章化し、既存の画面へ結果を返す。成功時だけでなく、他人の入力、削除済み/古い対象、生成できない場合、通信失敗の場合も、誤った本文や成功表示にしないことを対象検査で確認する。

10/03の第一到達目標は、認証された本人の保存原入力からPieceのプレビューまで、対象開発環境で一往復できること。コード接続と模擬保存・模擬認証による検査は途中成果であり、実環境での成功に置き換えない。実行・適用には対象環境と必要な権限を確認し、既存の許可範囲を超える公開API・DB・依存等の変更は具体的な差分を示して別判断とする。環境や承認待ちでも実装できる独立部分は進め、全作業を止めない。

第一到達目標が成立したら、そのまま同じcanonical本文の保存→履歴からの再取得へ伸ばす。保存・履歴の往復は次の優先段階、native画像保存・共有は後続の既存必須残件として保持する。来週一週間に全経路の商品合格を保証する計画ではなく、どこまで通り、どこから未接続かを10/03に明確にする。

最初の接続単位を原入力に絞ることは、許可された回答・補足・refined-sourceの実装を廃止する決定ではない。元入力と補足を区別する既存契約は維持する。Emlisの生成した応答文をsourceへ流用しない。quote/short_essay/declarationの提供範囲も勝手に削らない。
