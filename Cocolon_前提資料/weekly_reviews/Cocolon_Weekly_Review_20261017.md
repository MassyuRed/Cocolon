## 3. 議題3 — 不足、原因、修正対象、完了条件

### 3.1 現行の実行経路と、残すべき実装

通常入力は`InputScreen`で本人・感情・categoryとともに保存され、保存されたinput IDからthreadを開く。APIのthread serviceが本人所有の元入力、QUESTION、ANSWER、checkpoint、許可されたhistory/frameから要求を再構成し、CMEEが意味を準備する。本文はplan→projection→input-specific meaning→composition→Human Reception→表面・逆検証を通る。初回本文の成立後に問いを選び、serviceが観測・問いを保存し、RNが保存済み本文を表示する。

回答後は**ANSWER→MEANING_UPDATE→OBSERVATION／QUESTION**を順に保存する。回答を元入力へ連結して上書きせず、生成質問文を本人の根拠にしない。material update後の本文生成が失敗した場合、古い本文を新しい現在本文だと偽らず、checkpointは保持する。GETは再生成しない。意味変更がないときの保存本文再利用と、回答を読めない`ANSWER_UNREFLECTED`は別である。これは削るべき余計な機構ではなく、本人の意味と履歴を壊さないために残す責任である。

Emlis threadの回答・訂正・続行は、新規感情入力、花、通知、国家入力数、Astor queueを無断で増やさない。Emlis生成本文をAnalysis/Pieceの本人原入力へ格上げしない。各商品は独立した価値を持つため、Emlisの商品PASSや問い発動を他商品の原入力利用の新しい前提にしない。参照：[共有設計][S-SHARED]、[thread engine][S-ENGINE]、[service][S-SERVICE]、[surface][S-SURFACE]、[RN hook][S-HOOK]。

### 3.2 E01 — 言葉の認識から、本人の意味を失っている

**現在の不足：** source位置や文字列が保持されても、主体、事実／受け取り、現在の感情／未来の不確実、時点差、理由と対象が誤っていれば、下流は誤った意味を安全に表面化するだけになる。例01/02/03/04/08/09/10が具体的な証拠である。全engineが単一regexという説明も誤りで、汎用の語彙演算と優先順位、多数のsource根拠付き専用分解が併存している。

**修正する責任：** 既存`emlis_ai_grounded_observation_plan.py`の認識・節分解・主体／時点／極性／modality判定と、現行thread source/projectionの接続。文章作者へ推測を追加して上流欠落を隠さない。

| 必要な区別 | 今回の失敗と、具体的に閉じる対象 | 確認する対照 |
|---|---|---|
| 感情と、その対象・成立条件 | 休めた安堵、気を遣わない軽さをneutral eventやnegative feelingへ潰さない | 同じ意味の自然な言い換え、否定、条件付き、別時点を変えた入力 |
| 出来事と本人の評価 | 使われなかった事実と、努力に意味がなかったという本人の受け取りを分ける | 本人が断定した事実／気がした評価／他者が言った評価を区別 |
| 未来の不確実と現在の実感情 | 将来もう誘われないかもしれないことと、今の寂しさを一つのuncertain constraintにしない | 将来予測を否定しても現在の感情が消えない。現在感情の訂正が未来予測を勝手に変えない |
| 分からないという本人情報と自己評価 | 本人が述べた理由不明を、不明の対象・範囲を失った自己評価と同一視しない | 不明、言いたくない、まだ言葉にできない、単に未記載を同義にせず、既に分からないと述べた原因を再質問しない |
| 評価・充足と行為 | やってよかった・満たされた等をevent/factへ失わない | 05で通る語だけでなく自然な別表現、逆評価、他者評価、当時／今の差 |
| 時点間の変化 | 以前と今日の同じ本人の反応を関係として保持 | 過去の自己／他者の過去／仮定の未来を混ぜない。変化の理由を無根拠に足さない |
| 発話者・経験者・報告範囲 | 他者の喜びを本人の感情へ移さない | 他者報告、本人の引用、本人の応援と寂しさを各ownerへ保持 |

ここで必要なのは全日本語を一度に作り直す宣言ではない。まず今回の失敗を生む**共通の意味区別とその作用範囲**を確定し、同じ責任に属する自然な別表現まで修正する。fixture ID・サンプル文字列の特別分岐や、感情語を一つずつ増やすだけでは閉じない。誤認の原因が独立なら同じ変更へ混ぜない。各修正は下流の中心・本文・問い・訂正に届くところまで確認する。参照：[grounded plan][S-PLAN]、[thread projection][S-PROJECTION]。

### 3.3 E02 — 例03の無応答：選択した意味とReceptionの参照が一致しない

実例03は`LIMITED_RECEPTION_CAPABILITY_GAP_STOP`で停止した。内部の経路は次のとおりである。

1. contrastに必須の`OBSERVE_TENSION`と、その一端に任意の`OBSERVE_CENTER`がある。
2. `emlis_stage1_response._bind_reception_moves`は対象・支援が重なる両方のcontributionをReception basisへ集める。
3. thread projectionは両方を引き継ぐ。
4. `emlis_input_specific_meaning._limited_meaning_outcome`はLayer1の必須contributionだけを保持する。
5. contractsの`resolve_limited_reception_aggregate`が、Reception basisは保持したLayer1集合内でなければならないという条件で拒否する。

**不足は利用者が情報を出さなかったことではなく、意味選択と参照集合の内部不整合である。** 直す場所は既存response binding、meaning selection、projectionの責任境界。最終的に選択された正当な意味へReceptionを結び、必須の対象・支援・両端が欠落せず追跡できるようにする必要がある。参照：[response][S-RESPONSE]、[meaning][S-MEANING]、[projection][S-PROJECTION]、[contracts][S-CONTRACTS]。

完了条件は、同じ元入力で初回Layer1/2が出ることに加え、安堵と寂しさ、それぞれの対象・時点・不確実さが正しく残り、内部の保持宣言だけで終わらないこと。上流の意味誤認はE01で別に閉じる。subset検査の解除、必須意味の削除、参照の偽造、汎用fallbackの挿入を修復として認めない。

### 3.4 E03 — 例04の無応答：本人の「理由が分からない」が本文へ届かない

例04も同じ停止codeだが、原因はE02と異なる。

1. 原文のしんどさはfeeling、理由が分からない節はself_evaluation/uncertainへ分類される。
2. thread projectionは本人が明示した不明をrequired unknownとして保持し、limited foregroundに含める。
3. 本文contributionは`OBSERVE_BURDEN`と`OBSERVE_CENTER`で、通常の二節には結び付くがunknownへのtraceを持たない。
4. contractsの`source_explicit_epistemic_unknown_object_ref`は、認められた直接のuncertainty node等の厳しい条件だけを扱う。今回のself_evaluation分類は適合しない。
5. compositionがforeground各objectにLayer1 traceを要求し、unknownのtraceが空のため停止する。

修正は、**本人の実感情と、本人にも理由が不明という情報を別々に正しく認識し、既存意味ownerから表示まで根拠を通すこと**。その不明を「自己評価」へ変えたり、理由を創作したり、unknownを消したり、本文にないtraceを付けたりしない。厳しいunknown契約をどの正当なsource表現で満たすかを確認し、契約を緩めるだけの修正にしない。参照：[projection][S-PROJECTION]、[composition][S-COMPOSITION]、[contracts][S-CONTRACTS]。

完了条件は、詳細な原因を断定しない最小観測と、その状態に結び付いた受け取りが返ること。既述の不明をそのまま聞き直す問い、調査不能を本人の入力不足へ転嫁する説明、質問だけでの返答は不可。E02と同じcodeだから同じ修正で両方直ったと扱わない。

### 3.5 E04 — 中心選択と「Emlisから」の内容形成が足りない

limited側では複数の状態が`ATTENTION/ATTEND_TO`等へ縮まり、Human Receptionの有限operationが「材料として受け取る」「両端を保持する」「未完了のまま置く」「選択を尊重する」等を実現する。評価・receivedの専用経路もあり、05〜07等で限定的な改善が出る。しかし、その入力をどう読んで何を伝えるかという内容が弱い場合、語尾を変えても同じ処理説明が残る。

具体的に必要な仕事は以下である。

1. E01で得た複数の意味のうち、今回本人にとって重要な区別・関係を既存meaning ownerで選ぶ。根拠のある中心と、捨ててよい周辺を区別し、surfaceの文字数都合で中心を決めない。
2. その選択から、本人の経験に対する受け取りの内容を作る。原文を引用する義務と、引用以外に伝える内容があることを別に確認する。
3. Layer1は確認可能な根拠、Layer2はそこから受け取ったこと・考えたこと・伝えることの連続にする。三文や決まった接続語へ固定しない。
4. 語義説明、一般的な共感、肯定、助言、診断、他人の心の代弁、無根拠な因果へ逃げない。根拠が足りない点は不明として残す。
5. 同じ正しい意味を自然に言い換えた本文は許容し、主体・否定・時点・対象・意味関係を変えた本文は拒否する。writerとcheckerが同じ形を再現できることだけを理解の証明にしない。

確認対象は初回だけでなく、回答・訂正後のLayer1/2。本文の読み取りでは、**入力のどこを読んだ結果、この焦点と受け取りになったか／別の入力へそのまま貼り替えられないか／本人の言葉より何が明確になったか**を現物で判定する。これは新しい自動採点器を作る仕事ではない。参照：[意味決定設計][S-MEANING-DESIGN]、[meaning][S-MEANING]、[Human Reception][S-HR]、[詳細設計§35][S-EMLIS-DESIGN]。

### 3.6 E05 — 問い候補と回答理解を、同じ意味の更新として閉じる

現行`emlis_question.py`は242行で、実行される候補種は次の2系列である。

| 候補 | 現在の条件 | 覆っていない責任 |
|---|---|---|
| PERSONAL_RECEIVED_MEANING | 有限な受領イベント、事実として認められる節、同sourceの反応、本人の意味がまだ書かれていない等 | 任意の日常文の重要な意味不足、複数解釈、理由・価値・関係の未知の一般的選択 |
| PERSONAL_OUTCOME_STANDARD | 有限の全体ゼロ成果評価と、別に明示された実行済み活動のpair、厳密なfield coverage等 | 一般の評価基準・願望・達成感の不足全般 |

候補なしENDは「本人を十分理解した」ではなく、この有限選択で候補が得られなかった状態である。base observation planの`question_policy.allowed=false`だけを見てthreadの問いが削除されたと判断しない。現在の上限はFree/Plus1問、Premium逐次3問。Premiumでも更新本文の成立、本人continue、残枠が必要である。

質問文の種類を増やすだけでは不十分。回答parserも有限で、本人感情・受け取った見方・now/then・明示引用による訂正／撤回・一部の基準回答等を扱う。他時点・曖昧時点・未対応構文を勝手に飲み込まずunresolvedにする保護は残す。必要な仕事は、**問う対象を意味上の不足として選び、その答えが実際にどの意味・中心・本文を更新するかまで同じ変更範囲で実装すること**である。

| 状態 | 必要な動作 | 不可とする代替 |
|---|---|---|
| 入力に既に書いてある | 既存根拠から読む | parserが読めないため本人に同じことを再説明させる |
| 本人が分からないと明示 | 不明自体を保持し、今分かる範囲で観測 | 不明を否定する断定、同じ「なぜ」の繰返し |
| 本人だけが答えられ、読みを変える重要不足 | 任意の一点を明確に問う。答える前も本文を返す | 情報収集の羅列、問いのための問い |
| 生成実装の不足 | 能力不足として修正対象に残す | 本人の入力不足や正常ENDへ偽装 |
| 回答が追加・訂正・撤回を含む | 独立sourceで対象と依存だけ更新 | 原入力の上書き、質問文を本人のwishへ昇格 |
| skip/stop/分からない | 正常終了・保持、強制しない | 同じ問いの再発、無回答をエラー扱い |

完成の証拠は、対象の元入力→初回本文→必要な一問／適切なEND→実回答→更新本文→保存GETを通し、回答前後の差が本人の追加情報に対応することである。03/04に機械的にASKを足すことではない。初回100件の全面PASSを問い作業の開始条件へ戻さない。参照：[question][S-QUESTION]、[answer update][S-ANSWER]、[詳細設計Q1/Q2/Q3][S-EMLIS-DESIGN]。

### 3.7 E06 — 回答・訂正・撤回の保持欠落を初回と別商品にしない

### 6.1 問題は反省文の不足ではない

Mashは商品品質・観測・問いの定義を既に提示している。華恋が今回負うべき責任は、それを読んだと述べることではなく、現在のコードと出力のどこが満たしていないかを特定し、既存の是正が繰り返されている理由を実装・完成判断へ戻すことである。

### 6.2 先の説明を訂正する

- 「進め方を組み直す必要がある」を新しい判断のように提示した点は不適切だった。同種の判断は繰り返し記録されており、必要なのはその未履行を現行の原因と完了条件へ具体化することだった。
