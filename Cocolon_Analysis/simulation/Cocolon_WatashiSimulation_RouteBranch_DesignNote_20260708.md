## 0. 結論

「わたしシミュレーション」は、わたしマップで見えた役割・思考・行動ルートをもとに、

```text
もしこの場面で、少し違う選び方をしたら？
```

を試しに見るためのシステムである。

これは、自己分析を「あなたはこういう人です」で終わらせないための構想である。

Cocolonのわたしマップは、ユーザーに固定的な性格診断を返すものではない。  
ユーザーが過去入力の蓄積から、場面ごとに立ち上がりやすい役割、思考、行動、負荷、分岐可能性を見られるようにする。

「わたしシミュレーション」は、その先にある。

```text
現状の役割を知る
↓
その役割が作る現在ルートを見る
↓
分岐点を選ぶ
↓
別ルートを試しに見る
↓
気に入ったルートを保存する
↓
必要ならPiece化する
```

これは、今の自己ルートを消す機能ではない。  
今の自己ルートを残したまま、そこから派生・分岐する別ルートを見る機能である。

Cocolonにおける三大中核との関係は次のように整理できる。

```text
EmlisAI:
  今の入力を読む。

問いシステム:
  足りない情報を問いで取りに行き、わかったふりを防ぐ。

Piece画像化:
  入力の核を外へ持ち出せる表現物にする。

わたしシミュレーション:
  わたしマップ上の役割ルートから、別の自己ルートを試しに見る。

Analysis / わたしマップ:
  入力の蓄積から、役割・ルート・分岐可能性を見える化する。
```

本資料では、まだ本格設計・実装順・DB schema・UI確定は行わない。  
現時点で決まった構想、価値、境界、危険、将来の詳細化候補を残す。

## 1. この構想が生まれた背景

自己分析で一般的なのは、次のような出力である。

```text
あなたはこういう人です。
あなたにはこういう傾向があります。
あなたはこういう性格です。
```

Cocolonのわたしマップは「役割システム」で分析するが、単に役割や行動パターンを提示するだけなら、一般的な自己分析と大きく変わらない。

Mash様は、自己分析の目的について次の仮説を置いた。

```text
ユーザーは、自分を理解したいだけではない。
自分を理解したうえで、可能なら修正したい、変えたい、別の自分を探したい、という気持ちを持つ場合がある。
```

もちろん、これは全ユーザーに当てはまる前提ではない。  
しかし、一定数のユーザーには当てはまる。

その場合、自己分析は次で終わってはいけない。

```text
現状を知る
```

その先に必要なのは、次である。

```text
現状を知ったうえで、
もし自分の一部を少し変えたら、
どんな思考や行動パターンになりそうかを一緒に考える。
```

この発想から、Mash様は「自己着せ替えシステム」のような感覚を話した。  
華恋は、それをCocolon向けに次の名称で受け取った。

```text
わたしシミュレーション
ルート分岐システム
```

## 2. 名前と概念

### 2.1 機能名候補

現時点で最も強い名称候補は次である。

```text
わたしシミュレーション
```

理由は、ユーザーが直感的に「自分のもしもを試す機能」と理解しやすいためである。

内部概念としては、次を使う。

```text
現在ルート
分岐点
別ルート
目標ルート
ルート分岐
```

### 2.2 ユーザー向け表現候補

```text
今のルート
別ルートを見る
この分岐で試してみる
このルートを保存する
別の動き方を見てみる
もしものわたしを見る
```

### 2.3 避けたい表現

次の表現は、自己否定・改造・治療・矯正に見える可能性があるため避ける。

```text
自分を治す
自分を改善する
性格を矯正する
理想の自分に変わる
正しいルート
間違ったルート
あなたはこう変わるべきです
```

Cocolonで扱うのは、正解ルートや人格改造ではない。  
あくまで「今の役割が作るルートを残したまま、別ルートを試しに見る」ことである。

## 3. ギャルゲー / 恋愛シミュレーション的な直感

Mash様は、この構想を聞いて「ギャルゲー」「恋愛シミュレーション」のルート分岐を想起した。

これは比喩として非常に有効である。

一般的な恋愛シミュレーションでは、

```text
選択肢
↓
関係性変化
↓
ルート分岐
↓
エンディング
```

が起きる。

Cocolonのわたしシミュレーションでは、

```text
選択肢
↓
役割の動き方が変わる
↓
思考・行動ルートが分岐する
↓
別の自己可能性が見える
```

となる。

ただし、Cocolonでは「攻略」や「正解ルート」を作らない。  
相手を攻略するのではなく、自分の中にある役割・思考・行動の流れを見て、別の動き方を試しに見る。

この比喩は、設計者間の理解補助として使える。  
ただし、ユーザー向けに過度にゲーム的な言い方をすると、自己理解の重さや安全境界を軽く扱っているように見える可能性があるため、正式UIでは慎重に扱う。

## 4. 解く問題

この機能が解く問題は次である。

```text
自己分析で「あなたはこういう傾向です」と言われても、
ユーザーはその先にどう扱えばいいか分からない。
```

わたしマップが役割や行動パターンを出しても、ユーザーには次の疑問が残る。

```text
じゃあ、どうしたらいいの？
この自分を変えられるの？
変えるとしたら、どこをどう変えるの？
別の選び方をした自分はどうなるの？
今の自分を否定せずに、別の可能性は見られるの？
```

「わたしシミュレーション」は、この問いに対して、断定や行動指示ではなく、別ルートとして候補を見せる。

```text
この役割を少し違う方向へ動かすなら、
こういう思考や行動ルートも候補として見えます。
```

つまり、これは「自己分析の先」を作るための機能である。

## 5. 基本思想

### 5.1 今の自己ルートを否定しない

現在の役割やルートは、ユーザーがこれまで生きる中で何かを守るために働いてきた可能性がある。

たとえば、

```text
場を整える人
相手を優先する人
後から一人で抱える人
ちゃんとしようとする人
```

といった役割は、単なる欠点ではない。  
関係を壊さない、場を保つ、責任を果たす、自分を守るなど、何らかの役割を果たしている場合がある。

そのため、Cocolonは「今のルートを消す」とは言わない。

```text
今のルートは残す。
そのうえで、別ルートを試しに見る。
```

### 5.2 予測ではなく、仮想ルートである

わたしシミュレーションは未来予測ではない。

```text
こうすればあなたはこうなります。
```

とは言わない。

言えるのは、

```text
この役割を少し変えると、こういう思考・行動ルートが候補として見えます。
```

までである。

### 5.3 行動指示ではなく、ルート記述である

Cocolonは、ユーザーに具体的な行動命令をしない。

避ける例:

```text
次から相手にこう言いましょう。
この場面では必ず断りましょう。
あなたはこう行動すべきです。
```

望ましい例:

```text
この別ルートでは、相手に合わせる前に、自分の違和感を一度確認する動きが入ります。
```

### 5.4 正解ルートを作らない

ゲーム的なルート分岐の楽しさはあるが、Cocolonでは正解ルートやハッピーエンドを提示しない。

代わりに、次のような表現を使う。

```text
負荷が少なそうなルート
自分を後回しにしにくいルート
相手との距離を保ちやすいルート
今の役割を残したまま、少し違う動き方をするルート
```

## 6. 基本UX案

現時点の基本UX案は次である。

```text
1. わたしマップを見る
2. 役割カードが並ぶ
3. 役割を1つ選ぶ
4. 現在ルートを見る
5. 分岐点を選ぶ
6. 別ルートを生成する
7. 現在ルートと別ルートを比較する
8. 気に入ったルートを保存する
9. 必要ならPiece化する
```

### 6.1 役割カード一覧

例:

```text
最近よく出ている役割

・場を整える人
・ひとりで抱える人
・ちゃんとしようとする人
```

各カードには、次を表示する候補がある。

```text
よく出る場面
守っているもの
選びやすい行動
負担になりやすいところ
関連する入力期間
```

### 6.2 現在ルート表示

例:

```text
役割:
  場を整える人

よく出る場面:
  人間関係で相手の反応が気になるとき

現在ルート:
  相手の反応を見る
  ↓
  自分の違和感を後ろに置く
  ↓
  場は保てる
  ↓
  後から疲れが残る
```

### 6.3 分岐点選択

例:

```text
どこを少し変えてみますか？

A. 自分の違和感を後ろに置く前
B. 場を保とうとする前
C. 後から疲れが出た後
D. まだ選ばず、別ルートだけ見る
```

### 6.4 別ルート生成

例:

```text
別ルート:
  相手の反応を見る
  ↓
  自分の違和感も一度確認する
  ↓
  全部は言わず、小さく境界を置く
  ↓
  場を保ちつつ、疲れを少し減らせる可能性がある
```

### 6.5 保存

例:

```text
このルートを保存しますか？

・保存する
・Pieceにする
・今は保存しない
```

## 7. ルートの種類

わたしシミュレーションでは、最低でも次の3種類を分ける。

### 7.1 現在ルート

入力履歴・わたしマップ・役割システムから見えている、現在出やすい思考・行動パターン。

```text
現状、こういう流れが出やすいように見える。
```

これは観測された材料に基づく。

### 7.2 別ルート / 分岐ルート

現在ルートの途中で、別の選び方をした場合の候補。

```text
この分岐では、こういう動き方も候補になる。
```

これは仮想・シミュレーションであり、観測済み事実ではない。

### 7.3 目標ルート / 保存ルート

ユーザーが「この方向に近づきたい」と保存したルート。

```text
今すぐできるとは限らないが、この方向を試してみたい。
```

将来的には、保存した目標ルートと、その後の入力履歴の近さを照合することも考えられる。  
ただし、初期設計では未確定とする。

## 8. observed と simulated の分離

この機能で最も重要な境界の一つは、`observed` と `simulated` を絶対に混ぜないことである。

```text
observed:
  入力履歴から見えているもの。

simulated:
  もしもの分岐として生成したもの。
```

これが混ざると、わたしマップがユーザーの本当の状態を勝手に書き換える危険がある。

禁止例:

```text
別ルートを生成しただけなのに、以後のわたしマップで「あなたはこういう人です」と扱う。
保存した目標ルートを、現在の役割として扱う。
AIが生成した分岐ルートを、入力履歴から観測された事実として扱う。
```

望ましい扱い:

```text
現在ルート:
  入力履歴から見えている候補。

別ルート:
  試しに見る仮想ルート。

保存ルート:
  ユーザーが関心を持った方向。
  ただし現在状態の正本ではない。
```

## 9. 生成に必要な根拠

別ルート生成では、AIが勝手に「こうなりそう」と作ると危険である。

最低限、次の根拠metaを持つ必要がある。

```text
source_roles:
  どの役割カードから来たか。

source_patterns:
  どの入力履歴・行動パターン・役割ルートから来たか。

branch_intent:
  ユーザーが何を変えたいと選んだか。

branch_point:
  現在ルートのどこから分岐したか。

safety_scope:
  断定禁止 / 行動指示禁止 / 医療助言禁止 / 高慎重領域制限。
```

根拠が薄い場合は、強い別ルートを出さない。

例:

```text
まだ入力が少ないため、はっきりした別ルートではなく、軽い候補として表示します。
```

## 10. 高慎重領域での制限

恋愛、家族、健康、金銭、トラウマ、自己否定、安全隣接、暴力・被害・加害に関わる領域では、分岐ルートを慎重に扱う。

高慎重領域で避けること:

```text
具体行動を強く勧める
相手との関係を断定する
医療・治療のように見える助言をする
安全判断をAIが代替する
ユーザーの人格や未来を断定する
```

高慎重領域で許容しやすいこと:

```text
見方の置き方を少し変える
自分の感覚を確認する
距離の取り方を観測する
すぐ行動せず、言葉にして置く
```

表示温度例:

```text
この領域は慎重に扱う必要があるため、具体的な行動ルートではなく、見方の置き方として表示します。
```

## 11. ユーザー向け注意文

初回説明やヘルプでは、次のような温度で説明する。

```text
これは、今のあなたを否定するものではありません。
今ある役割が作ってきたルートを残したまま、
少し違う選び方をした場合の別ルートを見てみる機能です。
```

別案:

```text
わたしシミュレーションは、正解を決めるものではありません。
今の自分を消すのではなく、別の可能性を地図上に置くための機能です。
```

毎回長く表示すると邪魔になるため、初回説明・ヘルプ・詳細説明で扱う。

## 12. EmlisAIとの接続

EmlisAIは、入力直後の即時観測である。  
わたしシミュレーションは、EmlisAIの中に統合しない。

ただし、EmlisAI観測後に、わたしマップ上の役割ルートと接続できる場合は、導線を出す候補がある。

例:

```text
この入力は、わたしマップ上では「場を整える人」のルートにも近いかもしれません。
別ルートを見てみますか？
```

ただし、これは毎回出さない。  
条件候補は次である。

```text
わたしマップが十分育っている
今回入力と役割ルートの接続根拠がある
ユーザーに負担が少ない
高慎重領域で過度な行動示唆にならない
```

EmlisAIは「今を読む」。  
わたしシミュレーションは「今と過去から見える役割ルートの別分岐を見る」。  
この境界を保つ。

## 13. 問いシステムとの接続

分岐方向が曖昧な場合、問いシステムと接続できる。

例:

```text
この役割を少し変えるなら、近いのはどれですか？

- 自分の気持ちも置きたい
- 相手との距離を保ちたい
- 後から疲れない形にしたい
- まだ分からない
- このまま別ルートを見る
```

問いシステムは、ユーザーに長い追加入力を強制せず、必要な曖昧さだけを確認するための仕組みである。  
わたしシミュレーションでは、`branch_intent` を確認する用途で使える。

ただし、問いが多すぎると負担になるため、基本は短い1問に留める。

## 14. Piece画像化との接続

別ルートは、Piece化と相性が良い。

別ルートから生成できるPiece例:

```text
私は、場を壊さないために自分を後ろに置いてきた。
でも、これからは自分の違和感も一緒に連れていきたい。
```

または、

```text
今の自分を消したいわけじゃない。
ただ、同じ場面で別の選び方もできると知りたい。
```

ただし、Piece化する場合も、画像Pieceと同じく安全境界を守る。

```text
raw inputをそのまま画像化しない
Cocolonが整形・安全確認したexport-safe textのみ画像化する
ユーザー自由編集は許可しない
```

わたしシミュレーションからPieceへ接続する場合も、本文はCocolon側で整形し、外部共有可能な表現へ変換する。

## 15. Analysis / わたしマップとの関係

わたしシミュレーションは、Analysis全体ではなく、わたしマップの発展機能である。

現時点の整理:

```text
こころ天気 / 感情グラフ:
  感情の履歴・推移を確認する補助データ。
  コメントは最小限でよい。

わたしマップ:
  役割・思考・行動ルートを分析する中核。

わたしシミュレーション:
  わたしマップの役割ルートから、別ルートを試しに見る発展機能。
```

わたしマップを単なる自己分析で終わらせないために、わたしシミュレーションは重要な候補である。

## 18. 実装時に問題になりそうなこと

### 18.1 AIが勝手に理想ルートを作る危険

ユーザーの入力履歴にない理想像をAIが強く提示すると危険である。

対策:

```text
branch_intentをユーザーに選ばせる
根拠metaを保持する
強い断定を避ける
候補として表示する
```

### 18.2 自己否定を強める危険

別ルートが魅力的すぎると、現在ルートを否定されたように感じる可能性がある。

対策:

```text
今の役割も何かを守っている可能性を明示する
現在ルートを消さない
別ルートは正解ではなく候補として出す
```

### 18.3 行動指示に寄る危険

「こうしなさい」にならないようにする。

対策:

```text
行動命令ではなくルート記述にする
ユーザーが選ぶ余地を残す
高慎重領域では具体行動を弱める
```

### 18.4 高慎重領域

恋愛・家族・健康・安全隣接などでは、分岐生成が危険になりやすい。

対策:

```text
見方の置き方中心にする
具体行動を避ける
必要なら分岐を生成しない
```

### 18.5 依存性

ユーザーが毎回「別ルート」をAIに求めすぎる可能性がある。

対策:

```text
毎回自動では出さない
ユーザーが明示的に開く
生成回数や保存数をプランで制御する
```

### 18.6 わたしマップ正本の汚染

simulated routeをobservedとして扱うと、わたしマップの正本が壊れる。

対策:

```text
observed / simulated / saved を明確に分ける
AI生成ルートを現在状態として扱わない
保存ルートもユーザーの関心方向として扱う
```

## 19. 禁止事項

```text
・現在ルートを悪いルートとして扱う
・別ルートを正解として扱う
・ユーザーに行動を命令する
・人格や未来を断定する
・治療・矯正・医療助言のように見せる
・高慎重領域で具体行動を強く提示する
・simulated routeをobserved routeとして保存する
・保存ルートを現在状態の正本として扱う
・ゲーム的な攻略感を強く出しすぎる
・ユーザーを理想の自分へ急かす
```

## 22. 三大中核内での意味

```text

```

という体験を持てる。

## 25. 華恋の判断

この構想は、非常に有望である。

理由は、わたしマップが抱えそうだった問題を解けるためである。

```text
自己分析が「分かった」で止まる問題。
```

わたしシミュレーションは、その先を作る。

```text
分かった
↓
今の役割ルートを見る
↓
別ルートを試しに見る
↓
自分の可能性を地図上に置く
```

これは、単なる斬新さではない。  
問題解決と必要性がある。

ただし、危険も大きい。

```text
自己否定
人格改造感
行動指示
未来予測
治療・矯正化
simulatedとobservedの混同
```

これらを避けるため、Cocolonでは次を固定する。

```text
今の自己ルートを消さない。
別ルートは正解ではない。
分岐は仮想である。
ユーザーが選ぶ余地を残す。
observedとsimulatedを混ぜない。
```

この境界を守れるなら、わたしシミュレーションは、問いシステム・画像化Pieceに並ぶCocolonの強い差別化軸になり得る。
